Whoever keeps working on this project should keep this file up to date.

1. WHAT THE SYSTEM DOES
---------------------------------------------------------------
An ISP management system for a small/medium wireless internet provider.
Admins manage customers, plans and billing; customers buy internet
access; the system controls, through the ISP's own hardware, whether a
customer's router actually has internet access - automatically when they
pay, and automatically when their time runs out.

Three moving parts, three separate codebases:

  1. FRONTEND (this project)  - Nuxt 4, what admins and customers see.
  2. BACKEND                  - Django, the business logic and database.
  3. DEVICE-COMMS SERVICE     - Node.js, talks to the physical hardware
                                 (PowerBeam radios and MikroTik routers).
                                 Built and owned by a different developer;
                                 the frontend never talks to it directly.

     Frontend  <--HTTP/JSON-->  Backend (Django)  <--HTTP+WebSocket-->  Node service  <---->  Hardware

SIGN-IN (two doors: customers and staff)
  Customers and staff (super administrators, administrators, technicians, financial
  managers) sign in at DIFFERENT addresses, through DIFFERENT server
  endpoints, and each door admits only its own kind of account:

      /login          pages/login.vue          -> POST /api/auth/login/         customers only
      /staff/login    pages/staff/login.vue    -> POST /api/auth/admin/login/   staff only (all four staff roles)

  THE SECURITY IS ON THE SERVER, not in the pages (backend accounts/serializers.py,
  LoginSerializer / AdminLoginSerializer). Hiding a link protects nothing; what
  guarantees that someone at the customer page can NEVER be signed in as an administrator
  - even holding an administrator's correct e-mail and password - is that the customer
  endpoint checks the account's role and refuses an ADMIN:
    - the refusal is BYTE-IDENTICAL to a wrong password / unknown e-mail / inactive
      account ("Unable to authenticate with the given credentials."), so the answer can't
      be used to discover which e-mails exist or who is an administrator. Never add a
      distinguishing message anywhere (the frontend shows one calm message for every
      refusal - utils/loginError.ts).
    - the same holds in reverse: a customer's correct credentials at the admin door.
    - a "right account, wrong door" attempt is written to the audit log as
      LOGIN_WRONG_PORTAL (which door, the account's role, the IP). A plain wrong password
      is not logged. The password never appears in it.
    - the role compared is the application role (User.role), not is_staff/is_superuser.
  The frontend adds a second check: LoginForm refuses to keep a session whose role is not
  the door's, even though the server never returns one.

  THE ADMIN ADDRESS. /staff/login is not linked from anywhere a customer looks, carries
  <meta robots noindex,nofollow>, and is deliberately NOT in robots.txt (that would publish
  it). This is hygiene, not the protection - the address is in the public JavaScript, and
  the endpoint's refusal above is what actually keeps customers out.
  TO MOVE IT: change ADMIN_LOGIN_PATH in app/utils/authPaths.ts and rename
  app/pages/staff/login.vue to match (pages/ops/login.vue for '/ops/login'). Nothing else
  refers to the path. The backend path (/api/auth/admin/login/) is independent.

  WHO IS SENT WHERE (all in app/utils/authPaths.ts, as the plain function
  resolveAuthRedirect, so every case is testable; app/middleware/auth.global.ts only
  feeds it the current state):
    - signed out, any /admin/* page  -> the CUSTOMER sign-in (never reveals the admin one)
    - signed out, /login or /staff/login -> shown
    - signed in as a customer at /admin/* or /staff/login -> their own area
    - signed in as a staff member at /customer/* or /login -> the staff area
    - signed in as staff at a page their PERMISSIONS don't include -> the first page they
      can open (their dashboard if they have it; an account with no dashboard permission
      lands on the first area it does have; one with none lands on My Account)
    - an account that MUST CHANGE ITS PASSWORD (after a reset, 2.4) -> held on its account
      page (/admin/account or /customer/account) until it has chosen a new one
    - an administrator's SESSION ENDS (token refresh fails) or they LOG OUT -> the ADMIN
      sign-in; everyone else -> the customer one (composables/useApiFetch.ts, layouts)
  Paths are matched by segment: /administrator is not the /admin area.

  THE PAGES. components/auth/AuthShell.vue (split screen: brand panel + form; a compact
  header on phones), LoginForm.vue (shared by both pages, `portal` = customer|admin),
  PasswordField.vue (show/hide key, Caps Lock warning). The form: a visible busy state,
  one calm error message, the rejected password cleared and the cursor returned to the
  password field (the fields are disabled while a sign-in is in flight and a disabled
  field can't take focus, so the busy state ends BEFORE focus moves - this was a real bug),
  empty fields explained instead of a greyed-out button, `autocomplete="username"` /
  `current-password` for password managers, the show/hide key keeps focus in the field.
  Do not link the admin page from the customer page, and don't mention administrators there.

COLORS (the brand blue and the rest of the palette)
  Every color in the app is a design token in app/assets/css/tokens.css, exposed to
  Tailwind in tailwind.config.ts, so one edit re-colors every place that uses it.
      --color-primary     THE BRAND BLUE as a FILL, #0062CC (rgb 0 98 204) in the light
                          theme, taken from the AirFiber logo. White text sits on it. It is
                          the sidebar background, the sign-in brand panel, the selected
                          state of the toggle buttons (history range, Bandwidth Limit
                          tabs), the access-point markers on the map, the map legend.
                          DARK THEME: deepened to rgb 14 50 108 - at full brightness it
                          glared against the dark page, most of all across the sidebar.
      --color-primary-text THE BRAND BLUE as TEXT or a LINE on the page (stat-card icons,
                          the RX/TX chart line): `text-primary-text`. Light theme: the same
                          blue (it simply follows --color-primary). Dark theme: a LIGHT blue
                          (rgb 96 165 250, 6.7:1 on the dark surface), because a deep fill
                          colour is unreadable as text on a dark page. This is why fill and
                          text are two tokens: they want opposite things in the dark theme.
      --color-logo-tile   the light tile a logo sits on over a dark fill (white in light,
                          a softer slate in dark so it doesn't glare).
      --color-secondary   teal - the PRIMARY ACTION BUTTONS (.btn-primary), the
                          numbered command badges. NOT the nav color; to make buttons
                          follow the brand too, change this token.
      --color-accent      sky blue - focus rings, highlights and links.
      success / warning / error, background, surface, text-*, border - status colors
      and the neutral page palette. [data-theme='dark'] overrides most of these.
      NOTE: Tailwind's `dark:` variant follows the OS setting here, NOT the app's theme
      switch, so never use `dark:` classes - put dark values in tokens.css instead.
  TO RE-COLOR THE NAV (AND EVERYTHING THAT SHARES IT): change --color-primary - in the
  light theme (:root) AND its deeper shade in [data-theme='dark'] - written
  as three space-separated numbers "R G B" (not hex) so Tailwind can apply opacity
  (bg-primary/10). Pick a color that white text can sit on: the sidebar's text is
  white at 90%, so aim for a contrast of at least 4.5:1 with white (the current blue
  scores 5.8:1 for full white, 5.0:1 at 90%). A noticeably lighter blue needs the
  sidebar text opacities in components/shell/Sidebar.vue checked again.
  RULES FOR NEW CODE:
    - Use the Tailwind classes (bg-primary, text-secondary...), never a hex code.
    - Where a literal value is unavoidable (Leaflet markers, chart libraries) use
      tokenHex('primary') (a fill) or tokenHex('primary-text') (a line) from
      app/utils/themeColor.ts, which reads the token. A hex
      typed into a page is a copy that silently stops following the palette - the map's
      access-point markers and one chart line were still the old navy (#0F2747) after
      the nav changed until they were switched to tokenHex.
    - The map's other markers (green/red/grey for online/offline/unknown) are still
      literal hexes, deliberately: they are status colors, not brand colors.

2.3 Device-comms service (separate repository, different developer)
  Framework   : Node.js, single process (no framework - raw http + ws)
  Talks to    : PowerBeam radios over an encrypted WebSocket connection
                they open outbound to this service; MikroTik routers over
                plain HTTP polling (the router asks "what should I do?"
                every ~20 seconds and reports what it currently sees).
  Talks to    : Django's /api/internal/... endpoints, using
                INTERNAL_SERVICE_TOKEN
  We (the frontend/backend side) do not maintain this codebase. If
  something about how a PowerBeam or MikroTik is addressed, or the exact
  wire format Node expects, needs to change, that is a conversation with
  whoever owns that service - not something to patch around silently in
  Django.


2.4 ROLES, PERMISSIONS AND ACCOUNT MANAGEMENT
  (Where older sections of this file say "admin" or "administrators only", read: the staff
  who hold the permission for that area - the table below. The role names are only labels.)

  THE MODEL. There are five roles, but a role is a LABEL AND A STARTING POINT. What an
  account may actually do is its list of PERMISSIONS:
    SUPERADMIN   everything, always, plus superadministrator-only operations. Not governed by
                 a list - nothing in the app can take this access away. Django's /admin/ site
                 is not exposed to AirFiber staff; its URL redirects to the Nuxt staff sign-in.
    ADMIN        starting template: operational access except the audit log and staff-account
                 management/deletion. A superadministrator may explicitly grant staff.manage;
                 permanent subordinate deletion separately requires staff.delete_subordinates.
    TECHNICIAN   template: devices (incl. console and device passwords), access points,
                 unregistered devices, MikroTik routers, a read-only look at customers.
    FINANCE      template: payments (view + record), revenue, read-only customers and
                 subscriptions.
    CUSTOMER     own data only; has no staff permissions.
  When a super administrator creates a staff account the permission checklist is pre-filled
  from the chosen role's template; they tick extra permissions or untick ones the person
  shouldn't have, and what they save is EXACTLY what the account gets.

  WHERE IT LIVES (one definition each - change it there, not at call sites):
    backend/accounts/roles.py     the role names (pure Python)
    backend/accounts/access.py    the permission CATALOG, the role TEMPLATES, dependency
                                  handling (normalize), what an account effectively holds,
                                  which notifications and dashboard sections it sees (pure
                                  Python - unit-tested without Django)
    backend/common/permissions.py permission_required(key), staff_read_write(view, manage)
    frontend/app/utils/authPaths.ts      which PAGE needs which permission (ADMIN_PAGE_RULES),
                                         landing pages, the route guard
    frontend/app/utils/permissionPicker.ts   the picker's tick/untick rules
    frontend/scripts/check-access.mjs    tests for both (npm run check:access); it holds a
                                         COPY of the catalog - keep it in step with access.py

  THE PERMISSIONS (key - what it allows). A "manage" permission always includes its "view":
    dashboard.view                 open the dashboard (it shows only sections the account can see)
    customers.view / .manage       read customers / create, edit, deactivate, block internet, notes
    subscriptions.view / .manage   read / grant, renew, block, resume (connects/disconnects internet)
    plans.manage                   create, edit, delete plans (done from the Subscriptions page)
    payments.view / payments.record
    revenue.view
    devices.view / .manage         read / add, edit, configure, commands
    devices.credentials            view/set a device or access point's stored password (3.1.2)
    devices.console                the raw device shell (3.1.1)
    access_points.view / .manage
    unregistered_devices.view / .manage   the "unknown devices" queue and adoption (3.1.3)
    microtik.view / .manage        routers, leases, commands, speed limits
    suggestions.view / .manage     read / respond
    announcements.manage
    notifications.view / .send     read staff notifications / create notifications for customers
                                   (.send also shows EVERY staff notification)
    audit.view                     read the audit log
  Some permissions pull others in (payments.record needs payments.view, customers.view and
  subscriptions.view, because its screen picks a customer and a subscription; devices.manage,
  microtik.manage and the like need customers.view for the same reason). Ticking one ticks
  what it needs; unticking one unticks what needs it; the server applies the same closure
  when saving, so no account can end up half-working.
  passwords.reset remains superadministrator-only. staff.manage is grantable to an Administrator
  for viewing/updating subordinate technician and finance accounts (and resetting their
  passwords); staff.delete_subordinates is a separate grant required for permanent deletion.
  Staff creation and permission grants remain superadministrator-only. The default ADMIN
  template includes neither staff-management permission.

  HOW IT IS STORED. User.staff_permissions (JSON). NULL = "never customised, follow the
  role's template" - what every account that existed before this feature has, so they kept
  exactly the access they had (and accounts made in tests with create_user(role=...) work).
  A list = exactly those (+ dependencies). [] = no access. Keys the catalog no longer knows are
  ignored; a damaged value falls back to the template. Read it ONLY through user.can(key) /
  user.permission_keys.

  HOW IT IS ENFORCED (backend). Each app's permission class asks user.can(...):
    customers      view / manage            plans          manage (anyone signed in may read)
    subscriptions  view / manage            payments       view / record
    revenue        revenue.view             devices        view / manage (+ credentials, console)
    access points  view / manage            unregistered   view / manage
    microtik       view / manage            suggestions    view / manage
    announcements  manage (all may read)    notifications  view / send (+ visibility, below)
    dashboard      dashboard.view, then each section needs its own view permission
  RULE FOR NEW CODE: "not an administrator" no longer means "a customer". Never write
  `if admin: ... else: <treat as customer>`. Decide each case: user.is_staff_member (any
  staff), user.is_customer, user.can(key). user.can() is False for every customer and True
  for every super administrator. Querysets use `if user.is_staff_member: return all` and
  leave "who may reach this endpoint at all" to the permission class.
  NOTIFICATIONS: a staff notification is one shared row; who sees it depends on type and on
  what the account can see elsewhere (NETWORK <- any network view permission, PAYMENT <-
  payments.view, SUBSCRIPTION <- subscriptions.view, CUSTOMER <- customers.manage,
  SUGGESTION <- suggestions.view). notifications.send sees all, including those addressed to
  individual customers. "Read" is shared by everyone who can see the row.
  DASHBOARD: GET /api/dashboard/admin/ always returns every key (zeros for sections the account
  can't see) plus visible_sections - the frontend draws only those.

  PASSWORDS - what a super administrator can and cannot do. Passwords are stored ONLY as
  one-way hashes; nobody, super administrator included, can read one. (An earlier design that
  stored a reversible copy was dropped on purpose.) A super administrator can:
    - see a masked password-state indicator in account management (no hash viewing endpoint);
    - RESET an account's password to the default, settings.DEFAULT_RESET_PASSWORD (env,
      default "0000"), behind a three-step confirmation enforced by the SERVER: tick
      "I understand", type the account's email exactly, re-enter the super administrator's OWN
      password. Limited to 30 attempts/hour. You cannot reset your own (use change password).
  Because the default is not secret, a reset account is flagged User.must_change_password and
  can do NOTHING but change its password: backend accounts/authentication.py
  (PasswordChangeAwareJWTAuthentication) refuses every request except profile,
  change-password, logout and refresh (403 with code password_change_required), and the
  frontend holds the person on /customer/account or /admin/account. A reset also revokes every
  session of that account. The default can never be CHOSEN as a new password. New staff
  accounts are created the same way by default (starting password -> must change at first
  sign-in; unticking is possible). A suspended customer can't change a password (writes are
  blocked) - restore them first.

  SAFETY RULES (server-side): you cannot change your own role or deactivate yourself; there
  must always be at least one active super administrator; accounts are only DEACTIVATED, never
  deleted (so the audit log keeps pointing at a real person); staff cannot be made customers.
  `manage.py createsuperuser` now makes a SUPER administrator. Migration accounts/0002
  promotes existing Django superusers who were ADMIN to SUPERADMIN; anyone else:
  `python manage.py promote_superadmin <email>`.

  THE SUPER ADMINISTRATOR'S SCREENS (under /admin/superadmin/, reached from the top-bar Admin Menu):
    Staff Accounts      pages/admin/superadmin/staff.vue - create, edit role/permissions,
                        deactivate/reactivate, reset password. The permission
                        picker is components/domain/PermissionPicker.vue.
    Customer Accounts   .../credentials.vue - customer identity/account details, masked password state, and reset.
    Audit Log           .../audit-log.vue - needs audit.view (a super administrator has it).
  Everybody on staff has My Account (pages/admin/account.vue): profile, what the account may
  do, change password. API (all /api/auth/): permissions/ (catalog), staff/, staff/<id>/,
  staff/<id>/reset-password/, customer-credentials/,
  customer-credentials/<id>/reset-password/ (password-hash routes removed 2026-11-05).
  audit-logs/. Everything except audit-logs/ requires the SUPERADMIN role itself (not a
  permission) and is invisible to everyone else (403).

  WHAT THE FRONTEND DOES WITH IT. Login and /api/auth/profile/ return `permissions` (the full
  effective list) and must_change_password. The sidebar shows only pages the account may open
  (layouts/admin.vue filters by canOpen); buttons that change things are hidden unless the
  account holds the matching "manage" permission (usePermissions().can); big device/network pages
  show a "view-only" notice (components/feedback/ReadOnlyNotice.vue) instead of hiding every
  control - the server refuses any change the account may not make. The permission list
  is refreshed from the server when the admin layout opens, when the tab regains focus (max
  once a minute) and after any 403 (max once per 30 s), and a page the account just lost is left
  automatically. THIS IS ONLY WHAT IS SHOWN; the server checks every request again.
  To ADD A PAGE: add it to ADMIN_PAGE_RULES in authPaths.ts (a page with no rule is
  super-administrator-only; check-access.mjs fails if a page under pages/admin has none).
  To ADD A PERMISSION: add it to accounts/access.py (and to a template if it belongs in one),
  use it in the endpoint's permission class, copy it into check-access.mjs, add tests.

2.5 AUDIT TRAIL AND LOGGING
  AUDIT TRAIL (common.AuditLog). One append-only table answering "who changed what, when, from
  where": action, the actor (a link AND a copy of their email, name and role - so the record
  stays true after the account is renamed, demoted or deleted), the target record, `changes`
  (before/after), IP address, browser, HTTP method and URL, status code, and the REQUEST ID.
  Rows can't be edited or deleted by the application (AuditLog.save/delete refuse).
  Everything funnels through common/audit.py write_entry(), which NEVER raises: if the audit
  write fails, the failure is logged ("isms.audit", ERROR) and the real action carries on.
  THREE THINGS WRITE ROWS:
    1. log_action(actor, "ACTION", obj, changes) - hand-written rows for meaningful events
       (these existed before; they now also record IP/request id automatically).
    2. Model signals (common/audit_signals.py) - whenever a signed-in STAFF member creates,
       edits or deletes a tracked record, a row "<model>.created/updated/deleted" with the
       exact fields changed {field: [before, after]}. Tracked: User, Customer, Plan,
       Subscription, Payment, Device, AccessPoint, DeviceConfiguration, DeviceCustomerAccess,
       UnregisteredDeviceSighting, MikroTikRouter, Announcement, Suggestion (TRACKED_MODELS -
       add a model there to audit it). NOT tracked: changes by customers or by the system
       (heartbeats, router reports, the expiry sweep - there is no staff member in the request),
       and derived rows (leases, queued router commands, device commands, metrics, notifications).
    3. Request middleware (common/middleware.py) - the safety net: a staff WRITE
       (POST/PUT/PATCH/DELETE under /api/) that produced no row gets "API_WRITE"; a refused one
       (401/403) gets "API_DENIED"; a server error gets "API_ERROR". Ordinary validation
       failures (400/404) change nothing and are not audited. Reading is never audited.
  SECRETS NEVER ENTER THE TRAIL (common/audit_helpers.py): any field whose name contains
  password, token, secret, credential, encrypted, signature, private_key or api_key is shown only
  as ["(hidden)", "(changed)"] - the fact it changed is kept (compared internally by real
  value), the value never is. Fix a leak by editing SECRET_NAME_PARTS there.
  Other action names: STAFF_LOGIN (every staff sign-in), STAFF_CREATED, STAFF_UPDATED,
  STAFF_PASSWORD_RESET / CUSTOMER_PASSWORD_RESET (+ _REFUSED when the confirmations failed),
  PASSWORD_HASH_VIEWED, LOGIN_WRONG_PORTAL, and the pre-existing CUSTOMER_*, MIKROTIK_* ones.
  READING IT: GET /api/auth/audit-logs/ (needs audit.view) and the Audit Log page - filter by
  person, role, action, record, date range, request, free-text search; "Show everything from this
  request" follows one click across rows.
  The client IP comes from X-Forwarded-For counted from the END by AUDIT_TRUSTED_PROXY_COUNT
  (default 1 = one proxy such as Heroku's router; 0 = ignore the header) because a client can
  forge the start of that header.

  LOGGING (for debugging). Every request gets a REQUEST ID (a sane caller-sent X-Request-ID
  is kept, else one is generated) which is on every log line, on every audit row and in the
  X-Request-ID response header (the frontend appends a short form to server-error messages:
  "(reference 4f9c2a1b)"). Log lines look like
    2026-11-02 10:15:03,214 INFO isms.audit [req=4f9c... user=ada@isp.com] AUDIT action=customer.updated ...
  Loggers: isms.request (one line per request: method, path, status, ms, who, IP; 4xx auth
  refusals WARNING, 5xx ERROR, Node's/routers' routine polling DEBUG), isms.audit (one line per
  audit row, and any failure to write one), isms.security (refused sign-ins - never the
  password - permission denials, password resets), plus each module's own logger.
  Env: LOG_LEVEL (default INFO; DEBUG shows the polling), LOG_FILE (also write a rotating file;
  LOG_FILE_MAX_BYTES default 10 MB, LOG_FILE_BACKUPS default 10). Console always. To trace a
  problem: take the reference from the error (or the X-Request-ID header), grep the log for it,
  and filter the audit log by it.


3. HOW THE CORE BUSINESS FLOW WORKS
---------------------------------------------------------------
This is the part most worth understanding end-to-end, because it spans
all three codebases.

3.1 Devices and access points
  - A PowerBeam radio can be configured as an Access Point (institution
    infrastructure - mounted on a tower, serves many customers) or a
    Station (one customer's receiver dish).
  - When a PowerBeam that Django doesn't recognise sends a heartbeat, it
    is recorded as an UnregisteredDeviceSighting. Django asks Node to
    classify it (access-point vs station) and to read its configured
    name; this can fail or be inconclusive ("uncertain"), and is retried
    automatically, throttled, until an admin resolves it.
  - An admin reviews these under Devices > Unregistered and either
    registers it as an AccessPoint, registers it as a customer's Device
    (a "station"), or discards the sighting.

3.1.1 Device console (raw shell)
  - An admin can open a live, interactive shell session on any PowerBeam
    Device straight from its detail page ("Console" button, top right) -
    log in with the device's own credentials, type commands, see the
    device's real output, just like SSH/telnet into it directly.
  - This proxies through Node exactly like everything else: Django never
    talks to the device directly. Node already had the underlying
    terminal/open, terminal/write, terminal/close endpoints built (a
    separate 'sys'-socket shell channel from the 'udapi' one used for
    status/config) - they just weren't wired to anything before
    2026-09-25. See devices/node_client.py (open_terminal/write_terminal/
    close_terminal) and DeviceViewSet.console_open/console_write/
    console_close.
  - Administrator only (devices.permissions.DeviceConsolePermission,
    deliberately separate from the normal DeviceOwnedPermission split so
    it can never be loosened by an unrelated change to that class) - a
    raw device shell is materially more sensitive than reboot/config-push.
  - Credentials are NEVER stored anywhere. Device has no password field by
    design - the admin enters username/password fresh every time they
    open a console, it's forwarded to Node for that one session, and
    discarded. Only the open/close of a session is audit-logged
    (DEVICE_CONSOLE_OPENED / DEVICE_CONSOLE_CLOSED), never the commands
    typed or the password.
  - Sessions are entirely in-memory on Node, keyed by a generated
    terminal_id - nothing is persisted in Django. A Node restart silently
    drops every open session; the frontend has no way to detect this
    except the next write/close call failing, which it surfaces as a
    normal error in the console panel.
  - The frontend (components/domain/DeviceConsole.vue) always calls
    console/close/ when the panel is closed, including via onUnmounted -
    an admin navigating away without explicitly disconnecting still frees
    the session, so it never sits open on the device indefinitely.

3.1.2 Device/access-point admin credentials (stored, viewable, editable)
  - Device and AccessPoint both now store their own admin login
    (devices.models.DeviceCredentialsMixin: admin_username,
    admin_password_encrypted + who/when it was last set). An administrator
    can view the actual password (not just "is one set"), generate a
    strong one, or set a specific one - "Password" button on the device
    detail page and on each row in Access Points. See
    DeviceCredentialsActionMixin.credentials on both DeviceViewSet and
    AccessPointViewSet (GET/POST .../credentials/), and
    DeviceCredentialsModal.vue on the frontend.
  - The password is encrypted at rest (common/crypto.py, Fernet -
    reversible, NOT hashed, since it has to be readable back in plaintext
    to actually be useful) under settings.DEVICE_CREDENTIAL_ENCRYPTION_KEY.
    Losing/rotating that key means every stored password becomes
    unreadable (decrypt_secret returns None, logged as a warning, not a
    crash) - back it up like any other production secret.
  - Generating/setting a password requires the device/AP to be currently
    connected - Node dispatches a live 'rpc-sys password_set' call (its
    already-built /internal/devices/{mac}/credentials/ endpoint, actions
    login/generate/set - wasn't wired to anything before 2026-09-27). A
    device that's never connected (no known MAC) can't have a password set
    this way - see 3.1.3 for how a device gets its FIRST password before
    it's ever connected to us at all.
  - Administrator only (devices.permissions.DeviceCredentialsPermission -
    its own class, same reasoning as DeviceConsolePermission: so it can't
    be loosened by an unrelated change elsewhere).

3.1.3 AP-scan device discovery ("unknown devices") and adoption
  - A SECOND, independent way an UnregisteredDeviceSighting can appear,
    alongside the original heartbeat path (a device that pinged us with an
    unknown MAC). Here, one of our own access points actively scans its
    own radio neighborhood (Node's discovery/ endpoint - the same
    udapi-refreshNeighbors AirOS "Discover" tool - already built, wasn't
    wired to anything before 2026-09-27) and reports back every device it
    can see, whether or not that device has ever spoken to US directly.
    Any MAC in that list not already a Device/AccessPoint becomes a
    sighting with source=ap_scan - shown in Unregistered Devices as
    "Unknown device" rather than "Unregistered device", since we've never
    heard from it at all. See devices.services.
    scan_access_point_for_unknown_devices and parse_discovered_neighbors.
  - IMPORTANT CAVEAT: parse_discovered_neighbors's field-name guesses
    (mac/ip/hostname/product/etc, with several aliases each) were NOT
    verified against a real captured udapi-getNeighbors/refreshNeighbors
    response - no sample was available when this was written. If real
    scans come back with different field names, widen the alias tuples in
    that function. Test this against a real AP before relying on it.
  - Runs automatically in the background, piggy-backed on the existing
    heartbeat-driven maintenance mechanism (common/maintenance.py -
    NO new scheduler/Celery/cron was introduced). Unlike the other
    maintenance steps this is a real over-the-air radio scan, so only
    settings.AP_DISCOVERY_SCAN_BATCH_SIZE access points (the least
    recently scanned, via AccessPoint.last_discovery_scan_at) get scanned
    per maintenance tick, cycling through all APs over
    settings.AP_DISCOVERY_SCAN_INTERVAL_SECONDS. An admin can also trigger
    one immediately - "Scan now" on an access point's row, POST
    /api/access-points/{id}/scan/.
  - Adoption ("Adopt" button on an unknown-device row, POST
    /api/unregistered-devices/{id}/adopt/) pushes an adoption request to
    the device using the discovering access point's live connection as a
    relay (Node's already-built discovery/adopt endpoint - see
    docs/adoption-mechanism.txt - also unwired before 2026-09-27).
    - The device isn't adopted yet, so it's assumed to still carry the
      SAME default/shared password our own gear ships with - the AP's own
      password is reused as the CURRENT login credential to authenticate
      the adoption call. If that AP has no password saved yet, the admin
      is asked for it once and it's saved on the AP going forward - even
      if the adoption call that follows then fails, so a retry never has
      to ask again.
    - Separately, the admin picks (or auto-generates) a NEW password to be
      applied to the device as part of adoption. This is held ENCRYPTED on
      the sighting itself (pending_admin_username/
      pending_admin_password_encrypted) until the sighting is later
      registered into a real Device via the existing register/ action, at
      which point it's transferred onto the Device's own credential fields
      automatically (services.transfer_pending_credentials) and cleared
      from the sighting.
    - adopt/ deliberately does NOT resolve the sighting (status stays
      PENDING) - it's a separate, retryable step from register/, tracked
      instead via its own adoption_status (not_adopted/adopting/adopted/
      failed). THE REAL ADOPTION SCRIPT/PAYLOAD IS STILL BEING FINALIZED
      OUTSIDE THIS CODEBASE - settings.DEVICE_ADOPTION_TARGET_PATH and
      DEVICE_ADOPTION_CONTROLLER_URL are explicit placeholders (see their
      settings.py comments) until that's ready, so failed/rejected adopt
      attempts are expected for now, not a bug. Node's response is stored
      on adoption_result (minus any credentials) for troubleshooting.

3.1.4 Device model, pictures and detected details
  WHERE THE INFORMATION COMES FROM. Node exposes two read calls that
  together describe a unit (both already existed; Django now uses both):
    wireless-mode  -> the product MODEL (e.g. "PBE-5AC-Gen2"), whether it
                      is an access point or a station, and its running
                      wireless settings (SSID, frequency, channel width).
                      The model arrives in the SAME response that decides
                      AP vs station, so tracking it costs no extra call.
    system-info    -> the model again, the HOSTNAME set on the device, and
                      its management network: IP address, subnet mask
                      (from the CIDR), default gateway, DNS servers,
                      static-vs-DHCP, time zone.
  The Wi-Fi passphrase (in wireless-mode) and the device's user list (in
  system-info) are never read or stored. When both calls report a model,
  the wireless-mode one wins (it is the full product code).

  WHEN IT IS READ. (1) The first time an unknown device is seen (the
  sighting records its model and name). (2) Registering a sighting copies
  the model onto the new Device - the admin can correct it in the form.
  (3) A registered device/AP that still has something unknown (no model,
  no wireless mode, no hostname) is asked again on its own heartbeat, at
  most once every 5 minutes, only FILLING BLANKS - it never overwrites
  what an admin typed, and a failure can never fail the heartbeat.
  (4) "Detect from device" on a device's Hardware card, and "Detect
  model" on an access point row, re-read it now and REPLACE what is
  stored. Routes: POST /api/devices/{id}/detect-identity/ and
  POST /api/access-points/{id}/detect-identity/ (admin only; 502 if the
  device can't be reached).

  PICTURES. The product catalog is Ubiquiti's own list
  (backend devices/data/device_icons_lines_products.json): each entry has
  an icon id, a product name, a product line and the SHORTNAMES devices
  report as their model. The backend looks a device's model up (exact,
  case-insensitive, then ignoring spaces/punctuation - it never guesses
  by prefix) and STORES three things on the record: icon_id,
  product_name, product_line. They are re-read every time the model
  changes, so correcting a wrong model corrects the picture; they are
  read-only through the API. The frontend only turns icon_id into an
  address - /devices/<icon_id>.png - and draws that image. If there is
  no icon_id (model not in the catalog), no such file, or the image fails
  to load, DeviceIcon draws a generic icon instead (a radio; a router for
  MikroTik). A failed image is remembered for the session so it is
  requested once, not once per row.
    - To add pictures: put <icon id>.png in frontend/devices/. Nothing
      else to change.
    - To recognise a new model: add its shortname to the catalog JSON in
      the backend (then re-save or re-detect existing devices, or run a
      small backfill like migration devices/0013).
    - A bare "P5B" is deliberately NOT matched: the catalog only lists
      P5B-300 / P5B-400 / P5B-620 (different antennas) and guessing would
      show the wrong product. It falls back to the generic icon.
    - Sightings show a picture too, but it is looked up on the fly from
      detected_model, not stored (it is stored once the device is
      registered).

  WHERE IT SHOWS. Device detail has three cards: HARDWARE (product, model,
  product line, MAC, serial, hostname, hardware and firmware version -
  editable: model, MAC, serial, versions), NETWORK (IP, assignment,
  subnet, gateway, DNS, time zone - display only, it is read from the
  device) and RECORDS (name, status, install date, location note,
  network device ID, notes - editable). The device and access-point
  lists, customer list/detail, unregistered-device cards and MikroTik
  cards all show the picture. The customers list shows the customer's
  device by product name.

  MAC ADDRESSES are stored lowercase, colon-separated everywhere
  (common/macs.py) - Device, AccessPoint and sightings normalise on save
  and the serializers normalise before checking for duplicates. Before
  this, an AP-scan or hand-typed MAC (uppercase) never matched Node's
  lowercase heartbeat MAC. Migration devices/0012 fixed existing rows.

  FIRMWARE VERSION. A unit does NOT report its own firmware in the metrics
  Node polls. The "firmwareVersion" in that response sits under
  wireless.peers[].common.identification and describes the unit at the
  OTHER end of the link: a station's peer is its access point, an access
  point's peers are its stations. So Django credits it to the record whose
  MAC matches the PEER's MAC - never to the unit that was polled - via the
  heartbeat's optional "peers" list (devices/services.record_peer_identities).
  The same entry also fills a blank model (its "product" is the full code,
  e.g. PBE-5AC-Gen2) and a blank IP. Firmware is overwritten whenever it
  differs (it is hardware-reported and changes on every upgrade); model and
  IP are only ever filled when blank. Two queries per heartbeat however many
  stations an AP has; writes only when something changed.
  >>> NEEDS A SMALL NODE CHANGE: today Node does not forward the peers, so no
  firmware arrives until it does. In djangoClient.js, function
  mapUdapiStatisticsToHeartbeat, add after the `const linkQuality` line:
      const peers = (snapshot.wireless?.peers || [])
        .map((p) => p.common || {})
        .filter((c) => c.identification?.mac)
        .map((c) => ({
          mac: c.identification.mac,
          product: c.identification.product,
          firmware_version: c.identification.firmwareVersion,
          hostname: c.hostname,
          mgmt_ip: c.mgmtIp,
        }));
  and add this line inside the `heartbeat = { ... }` object:
      peers: peers.length ? peers : undefined,
  Django already accepts it (and ignores it when absent), so the two sides
  can be deployed in either order. Serial number and hardware version were
  removed from the Hardware card: nothing reports them, so they were always
  blank (the columns still exist; nothing reads them).

3.2 MikroTik routers and client leases
  - A customer's Device (the receiver PowerBeam) sits behind a MikroTik
    router, which is what actually grants or denies that specific
    customer's internet access (by MAC address whitelist).
  - A MikroTik that Django has never seen registers as PENDING; an admin
    must approve it once. Once approved, it is trusted automatically on
    every future reconnect (e.g. after the Node service restarts) with no
    further admin action - see microtik/services.py
    verify_or_register_router. Revoking an approved router (MikroTik
    Management > MikroTiks > Revoke) takes effect immediately and stays
    revoked even if it reconnects.
  - Every ~20 seconds each MikroTik reports which client MACs it
    currently sees connected, and which MACs are on its "allowed" list.
    Django uses this to keep a MikroTikLease record for every device the
    router has ever seen - online or not, allocated to a customer or not.
    A device that stops being seen is marked offline but is NEVER
    deleted, so it isn't lost.
  - A lease with no matching customer is "unallocated" and appears under
    MikroTik Management > Needs allocation for an admin to assign.
  - As well as blocking/connecting a device that already has a lease
    record, an admin can send an "add to allowed list" or "block"
    command straight to a MAC address that a router has never actually
    reported seeing yet (MikroTik Management > Commands tab). This
    matters for infrastructure devices - an access point, a backbone
    link - that must never sit blocked just because they haven't shown
    up in a report: the admin can pre-authorise the MAC in advance, to
    one specific approved router or to all of them at once. Under the
    hood this creates a MikroTikLease if one doesn't already exist
    (offline, unallocated) purely so the normal pending/confirm
    machinery has something to track - see
    microtik/services.py:send_command_by_mac. This is the FIRST of what
    is expected to be several command types sent this way; if you add
    another, keep it going through the same "results: [...]" response
    shape (one entry per router targeted) so the frontend's handling
    doesn't need to special-case each command type.
  - Blocking/connecting a device is NOT instant. Django asks Node to
    queue the command; the router only picks it up on its next poll. The
    lease shows as PENDING until a later router report confirms the
    change actually took effect (or the command times out and is marked
    Failed). This is unavoidable given how the router protocol works -
    do not "optimistically" mark something Blocked/Allowed before it is
    confirmed.

3.2.1 Speed limits ("capping")
  WHAT IT IS. Each customer router (a MikroTikLease) can be held to an uplink
  and a downlink speed. UPLINK = data leaving the customer (uploads), DOWNLINK
  = data coming to them (downloads) - the customer's point of view, which is
  how a MikroTik queue is written. Speeds are stored and sent as WHOLE KBPS;
  the UI takes a number + kbps/Mbps/Gbps (utils/speeds.ts, SpeedInput.vue).
  DEFAULT means "no limit signalled": both speeds null, and the MikroTik is told
  nothing about speed for that device.

  STATE. lease.uplink_kbps / downlink_kbps (+ limit_source MANUAL|PLAN,
  limit_plan_name, limit_set_at). This is what Django LAST SENT, not what the
  router reports: the router's report carries no queue information and Node has
  no acknowledgement path, so a limit can only ever be QUEUED, never confirmed.
  Reports never touch these fields. The UI says "queued" and never "applied".

  THREE WAYS A LIMIT CHANGES
    1. By hand - MikroTik Management > Commands > 2. Bandwidth Limit. Pick a
       customer's router from the list (or type a MAC and choose its MikroTik);
       the device's CURRENT limit (or "Default") is shown; set both speeds, or
       "Remove limit (use default)". Endpoints: POST /api/microtik/leases/{id}/
       limit/ {uplink_kbps, downlink_kbps} and .../clear-limit/; or
       POST /api/microtik/commands/send/ with command_type set_limit|clear_limit
       (creates the device record if the MAC was never seen).
    2. By a plan - a plan has uplink_kbps/downlink_kbps (both null = default,
       both set = capped; one without the other is rejected). Whenever a plan
       is ACTIVATED (admin grant, customer purchase, renewal payment, admin
       resume) the customer is connected with a PLAIN reconnect, with the plan's
       speed RECORDED on that command (limit_change/uplink/downlink/plan_name).
       Once the router CONFIRMS the connection (its next report lists the MAC as
       allowed), Django sends the speed as its own speed_limit command
       (services.apply_deferred_limits, called from ingest_leases). It cannot go
       out together with the reconnect: Node keeps ONE pending action per
       device, so the second command would replace the first and the customer
       would never be connected. Cost: the speed lands one router check-in
       (~20-40 s) after the connection. Each reconnect is followed up exactly
       once (limit_followup_at is claimed atomically), and if the reconnect is
       never confirmed, no speed is sent and the admins are told.
       A plan with the default speed sends the MikroTik nothing about speed -
       EXCEPT when the router currently has a limit (from an earlier plan or by
       hand): then it is lifted after confirmation, because leaving a previous
       plan's cap on a plan that has none would be wrong. NOTE: activation
       REPLACES a manual limit. Restoring access without a plan (a plain
       Connect) leaves speed alone. Editing a plan's speed changes nothing for
       anyone already on it; it applies at their next activation (admins are
       told how many customers).
    3. Nothing else. Blocking never changes speed.

  COMMANDS. MikroTikCommand gained set_limit / clear_limit types plus
  limit_change (SET|CLEAR|""), uplink_kbps, downlink_kbps, plan_name. These
  can never be CONFIRMED, so they stay SENT ("Queued" in the history) and are
  excluded from the stale-command timeout. (A plan's reconnect also carries
  limit_followup_at: when its speed was sent. See above.) A speed command is refused (409)
  while an ACCESS command for the same device is awaiting confirmation, and a
  block/reconnect is refused for MIKROTIK_LIMIT_SETTLE_SECONDS (30) after a
  speed command - again because of Node's one-pending-action-per-device slot.
  Two speed commands in a row are fine; the second replaces the first.

  ADMIN NOTIFICATIONS (type NETWORK) - every speed event, in full:
    - limit set / removed by an admin: who, which customer/MAC, which MikroTik,
      now vs before (including whether the old one came from a plan), and that
      it is queued, not confirmed.
    - limit failed (Node down / rejected): the reason and that it is unchanged.
    - plan activation: the "Auto-connect" notice names the plan's speed and says
      it is sent once the router confirms the connection. After confirmation,
      "Speed applied" / "Speed limit lifted" per customer with the router, MAC,
      before and after; or "Couldn't apply speed" with the reason (Node down, or
      another command now pending for the device). A reconnect that fails or is
      never confirmed says the plan's speed was not applied either; "no router
      allocated" says the speed could not be applied.
    - plan created (always states its speed, even "default") and plan speed
      changed (before -> after, and how many current subscribers keep the old
      speed until their next activation).
  Every manual change is also written to the audit log.

  THE NODE CONTRACT (from Node's capping curl; one place on the Django side
  defines it: microtik/node_client.build_command_payload). POST to
  /internal/microtik/{signature}/commands/ with the usual bearer token:
      {"command_id": "speed-limit-<our command's UUID>",
       "command_type": "speed_limit",
       "mac_address": "ea:b5:b8:85:8a:90",
       "max_upload_mbps": 10,
       "max_download_mbps": 10}
  Django stores speeds in kbps and converts: 5000 kbps -> 5, 500 kbps -> 0.5.
  block/reconnect are unchanged ({"mac_address", "command_type"}). Django treats
  a speed_limit reply as accepted unless it says "accepted": false or carries an
  "error" (the reply shape is Node's to define); block/reconnect still need
  "accepted": true.
  REMOVING a limit (back to the default) is a DIFFERENT Node command, not
  speed_limit with zeros:
      {"command_id": "clear-speed-limit-<our command's UUID>",
       "command_type": "clear_speed_limit",
       "mac_address": "ea:b5:b8:85:8a:90"}
  It carries no speed values. (It was first built as speed_limit with both
  maximums 0 - a guess, because only the setting curl was known - and removal
  did not work until it was corrected to clear_speed_limit. 2026-10-09.)
  >>> ONE ASSUMPTION left, in build_command_payload: a speed that is not a whole
      number of Mbps (e.g. 512 kbps) is sent as a decimal (0.512). If Node only
      accepts whole numbers it will reject those (the command shows Failed and
      admins are notified); the fix is to limit the UI to whole Mbps. Likewise,
      clear_speed_limit is sent with only command_id, command_type and
      mac_address - add a field there if Node wants more.

3.2.2 Router reports, confirmation, and retries
  THE REPORT. Every check-in the router POSTs a form-style body that Node relays
  to Django unchanged (not JSON; microtik/parsing.parse_report):
      signature=<32 hex>&allowed_macs=<mac,mac,...>&metered_macs=<mac,...>&data=<ip|mac|host,...>
  `allowed_macs` is the whitelist and the SOURCE OF TRUTH for whether a device
  has internet; `data` is who is connected. A device is shown ALLOWED if its MAC
  is in `allowed_macs`, else BLOCKED - so a MAC that is dropped from the list
  looks blocked and any command that expects it ALLOWED can never confirm.

  THE BUG THIS DOCUMENT NOW GUARDS AGAINST (second time it has happened; the
  first was 2026-09-18). The parser only treats a fixed set of keys as field
  boundaries. When the router started sending `metered_macs=` between
  allowed_macs and data, that key was not in the set, so "&metered_macs=" was
  glued onto the LAST allowed MAC, which then no longer parsed as a MAC. Result:
  allowed devices showed as blocked, and a reconnect for the last one in the list
  failed after the timeout. Defences now in place:
    1. Every key the router sends is listed in parsing._KEY_RE. WHEN THE ROUTER'S
       SCRIPT GAINS A FIELD, ADD IT THERE (and to ParsedReport) in the same change.
    2. MAC lists are split on commas, whitespace AND "&" (split_mac_list), so a
       field that is not yet listed cannot corrupt the MAC next to it.
    3. Anything in a MAC list that is not a MAC is collected in
       ParsedReport.rejected_mac_entries and logged as a WARNING:
       "MikroTik report from <sig> has N unreadable MAC list entries (ignored)".
       If you ever see that line, the router's report has changed shape.
  `metered_macs` is parsed and carried on ParsedReport but NOT acted on. Its
  meaning is Node's to define; if it means "devices that currently have a speed
  limit applied" it is the missing feedback for speed commands (3.2.1) and could
  confirm them. Confirm with the Node author before relying on it.

  CONFIRMATION needs no polling: every report is compared with the command each
  of the router's devices is waiting on (ingest_leases + reconcile.py). A command
  is CONFIRMED when the report shows the expected state, stays pending while it is
  young, and FAILS only when it is older than
  MIKROTIK_COMMAND_CONFIRM_TIMEOUT_SECONDS (120) and the report still disagrees.

  RETRIES. Node keeps its queue of actions-for-routers IN MEMORY, so a Node
  restart (or a second instance answering the router's poll) silently loses an
  action Django already handed over - and the command would just wait out the
  timeout and fail, although re-sending is harmless (allowing/blocking a MAC
  twice equals once). So an unconfirmed block/reconnect is SENT AGAIN
  (services.resend_unconfirmed_commands, run first in the ~15 s maintenance sweep):
    - after MIKROTIK_RESEND_INTERVAL_SECONDS (30) without confirmation,
    - up to MIKROTIK_MAX_SEND_ATTEMPTS (4) sends in total,
    - only inside the confirmation window, and only while it is still the command
      its device is waiting on (a replacement supersedes it).
  A resend that Node refuses, or cannot be reached for, counts as an attempt but
  does NOT fail the command (Node may be mid-restart); the note is kept in
  error_message and cleared by a later success. The failure message says how hard
  it tried ("sent 4 times"), and the history shows "Tried N times". Speed commands
  are never re-sent: nothing could say whether one took.
  Separately, one request to Node is retried up to MIKROTIK_NODE_INLINE_RETRIES (2)
  more times, ~0.4 s apart, for a hiccup only (connection error, timeout, 502/503/
  504) - never for an answer from Node, because "no" will not change.
  Node's own error codes are shown in words (node_client._NODE_ERRORS): e.g.
  "microtik-not-registered" (HTTP 404) = Node has no session for the router, so it
  likely restarted and the router must check in again.

3.3 Plans, subscriptions and automatic access control
  - A Plan has a price and a length. Length is stored in MINUTES, so a
    plan can last 30 minutes, 2 hours, or 30 days - the admin UI takes a
    number and a unit (Minutes/Hours/Days).
  - A customer can only buy a plan, or be granted one by an admin, if a
    MikroTik device has already been allocated to them. Without a
    router there is nothing to connect them through.
  - The moment a plan becomes active (customer purchase, admin grant, or
    a renewal payment), the customer's router is sent a "reconnect"
    command automatically.
  - Subscriptions track an exact starts_at / ends_at timestamp, not just
    a date - this is what makes short plans meaningful. A background
    sweep (common/maintenance.py, piggy-backed on the constant stream of
    heartbeats/router-reports Node sends - no external cron needed) runs
    roughly every 15 seconds and disconnects any customer whose plan has
    passed its exact end time, sends them a notification, and reminds
    customers whose plan is about to expire (the reminder timing scales
    with the plan's length).
  - This whole automatic-connect/automatic-disconnect behaviour is gated
    by one Django setting, MIKROTIK_AUTO_ENFORCEMENT (default True). If
    set to False it becomes an emergency kill switch: subscriptions and
    payments still record normally, but nothing automatically touches a
    router. Manual block/connect by an admin always works regardless of
    this setting.
  - Every automatic action, and every failure (a command that couldn't
    be sent, or that a router never confirmed), generates a notification
    - to the admins for anything system-triggered, to the customer for
    anything that concerns their own service.

3.4 Revenue
  - "Revenue" is defined as the sum of COMPLETED payments, by the date
    the payment was recorded. This is computed live from the Payment
    table (payments/revenue.py), not cached anywhere, so it can never
    drift out of sync with the underlying records.
  - The admin Revenue page (Nav: Revenue) is deliberately minimal: the
    admin picks a period, a measure (revenue / number of payments /
    average payment), an optional split (by plan or by payment method),
    an optional comparison period, and a chart type. The page shows only
    what was picked - no fixed dashboard of numbers.

5. THINGS THAT ARE EASY TO GET WRONG (READ BEFORE CHANGING)
---------------------------------------------------------------
- PERMISSIONS, NOT ROLES. Never compare a role string ("ADMIN") to decide what someone may do;
  ask user.can("some.key") (backend) or hasPermission/can() (frontend). A role is only a label
  and a template (2.4). And "not an administrator" no longer means "a customer": a technician
  is neither - decide each case explicitly (is_staff_member / is_customer / can(key)).
- A NEW ENDPOINT needs a permission class that names its permission, or any signed-in user
  could reach it. A NEW PAGE needs an entry in ADMIN_PAGE_RULES (otherwise it is
  super-administrator-only, and npm run check:access fails). A NEW PERMISSION must be added to
  accounts/access.py, the endpoint, and the copy in scripts/check-access.mjs.
- THE FRONTEND ONLY SHOWS; THE SERVER DECIDES. Hiding a button or page is courtesy. Never rely on
  it for security, and never skip the server-side check because the UI hides something.
- PASSWORDS CANNOT BE READ BACK, by design. Do not "add a reveal" by storing a reversible copy
  (an earlier design did; it was removed): a database leak would then expose every customer's
  password, and many people reuse theirs. The supported tools are: reset to the
  default (which forces a change). Resetting must keep revoking sessions and setting
  must_change_password.
- must_change_password is enforced in accounts/authentication.py, which replaced the default
  JWT authentication class in settings. If you add an endpoint a person must be able to use
  while locked to the change-password step, add its path to
  ALLOWED_WHILE_PASSWORD_CHANGE_REQUIRED there - nothing else.
- AUDITING MUST NEVER BREAK A REQUEST. write_entry/log_action swallow and log their own errors;
  keep it that way. Don't put business logic inside audit handlers, and don't record secrets:
  extend SECRET_NAME_PARTS (common/audit_helpers.py) if you add a field that holds one. A secret
  field's real value is compared internally (SecretValue) but only a marker is ever stored -
  an earlier version masked both sides identically and so MISSED password changes entirely.
- Audit signals only record changes made while a signed-in STAFF member is in the request.
  A change made by a script, a management command or the Node service is intentionally not
  attributed to anyone. If a management command should be audited, call log_action yourself.
- Audit rows are append-only (AuditLog.save/delete raise). Don't add code that edits them; a
  bulk QuerySet.update/delete would bypass this guard, so don't write one either.
- X-Forwarded-For can be forged at its start. The audit IP is taken from the END, counting
  AUDIT_TRUSTED_PROXY_COUNT proxies; change that setting if the hosting setup changes (0 when the
  app is reached directly).
- A MikroTik lease's access_state (Allowed/Blocked/Pending/Unknown) is
  DERIVED from the router's own report, never set directly by Django
  except to PENDING when a command is queued. Don't add code that sets
  it to Allowed/Blocked directly - that would lie about hardware state
  Django hasn't actually confirmed.
- "Online" for a Device, AccessPoint or MikroTikRouter always means "the
  status says so AND the last report was recent enough" - never trust
  the stored status field alone, it is only ever updated when a report
  arrives, so a device that went silent would otherwise look online
  forever. Look for the *_offline_threshold settings and the
  is_actually_online()-style helpers already in each model.
- Subscription status (Active/Expired) is derived live from ends_at, not
  from the stored `status` field alone - the stored field only gets
  flipped to EXPIRED when the maintenance sweep runs. Any new code that
  reads a subscription's status should go through the model's
  effective_status property / the queryset's .active()/.expired()
  helpers, not compare `status == 'ACTIVE'` directly.
- The internal (/api/internal/...) endpoints are for the Node service
  only. They use a completely different auth mechanism from the rest of
  the API (a shared bearer token, not a user's JWT). Never point the
  frontend at them.
- Device console sessions (see 3.1.1) are stateful on Node only - Django
  holds no record of an open terminal_id at all. Don't try to "list open
  sessions" or reconnect to one from a fresh page load; the frontend
  always starts a brand new session via console/open/.
- Device/AP passwords (3.1.2) are encrypted with
  DEVICE_CREDENTIAL_ENCRYPTION_KEY - if that env var differs between
  environments (or gets rotated without a migration plan), every
  previously-stored password becomes silently unreadable (returns None,
  not an error) rather than throwing. Keep it consistent per environment
  and treat it as seriously as any other production secret.
- AP-scan discovery (3.1.3) is a REAL radio scan on live hardware, not a
  cheap DB query - that's why it's rate-limited per-AP
  (AP_DISCOVERY_SCAN_INTERVAL_SECONDS) and batched
  (AP_DISCOVERY_SCAN_BATCH_SIZE), unlike the other maintenance steps.
  Don't lower the interval or raise the batch size without thinking about
  how many APs you actually have and how disruptive frequent scans are to
  their normal operation.
- Device adoption (3.1.3) is genuinely expected to fail right now for real
  devices - the adoption script/payload it sends is a placeholder pending
  work outside this codebase (settings.DEVICE_ADOPTION_TARGET_PATH /
  DEVICE_ADOPTION_CONTROLLER_URL). Don't treat a failed adopt/ call as a
  regression until those are finalized and confirmed against real
  hardware.
- common/maintenance.py's sweep is what makes automatic disconnect work
  without a scheduler - it rides along on whatever heartbeat/report
  request happens to arrive next, throttled by MAINTENANCE_INTERVAL_SECONDS.
  There is also a `python manage.py expire_subscriptions` management
  command that does the same work, kept as a backup for real schedulers
  (e.g. Heroku Scheduler) - both are safe to run at the same time.
- icon_id / product_name / product_line (3.1.4) are DERIVED from the
  model and re-read on every save. Don't make them editable or set them
  by hand - change the model. If you bulk-update models with
  queryset.update() (which skips save()) the derived fields will not
  follow; re-save the rows or backfill them.
- The product pictures are NOT in public/ and NOT served by Django. They
  live in frontend/devices/ and nuxt.config.ts maps that folder to
  /devices/ with a nitro:config hook (Nitro needs an absolute path; a
  relative one is silently ignored). If pictures stop appearing, check
  that hook first, then the file name == icon_id + ".png".
- Customer.notes (internal admin notes) must never reach a customer: the
  serializer drops it for non-admins and rejects a non-admin writing it.
  Any new customer-facing endpoint that serializes a Customer must go
  through CustomerSerializer, not a hand-rolled dict.
- CustomerSerializer's summary fields (device_count, plan, router online,
  ...) are only computed on the customers endpoint
  (context["include_summary"]) because the same serializer is nested in
  subscription/payment/device responses, where they'd cost several
  queries per row. Don't turn them on globally.
- The router's report format is a contract with the router's script. When that
  script gains a field, add the key to parsing._KEY_RE. A key that is missing
  corrupts the field before it, and the symptom is far from the cause: allowed
  devices show as blocked and commands "fail". Watch the logs for "unreadable
  MAC list entries" (3.2.2).
- NEVER send two commands for the same device back-to-back. Node keeps one
  pending action per MAC, so the second silently replaces the first (this is
  why a plan's speed waits for the reconnect to be confirmed, and why Django
  refuses an access command right after a speed command, and vice versa).
- Speed limits are QUEUED, never confirmed (3.2.1). Don't add UI that says a
  limit is "applied"/"active" on the router, and don't add speed commands to
  the stale-command timeout - they'd all be marked failed.
- A plan's speed is both-or-neither (uplink and downlink). A half-set plan is
  treated as default. Don't "fix" this by allowing one direction without
  agreeing how Node should express an unlimited direction.
- Activating a plan REPLACES any manual limit on the customer's routers (and a
  default plan lifts one). If admins start wanting manual limits to survive
  renewals, that is a decision to make, not a bug.
- Run the backend tests with explicit app labels
  (python manage.py test devices customers microtik ...). The repo has
  stray duplicate copies of some apps nested under microtik/ and
  dashboard/ that make a bare "manage.py test" fail with duplicate-model
  errors; they are not in INSTALLED_APPS and should be deleted.

9. KNOWN ISSUES / NOT YET DONE
---------------------------------------------------------------
- THE PERMISSIONS/AUDIT WORK HAS NOT BEEN RUN END TO END. It was developed without a Django
  install or node_modules, so only the pure-Python tests (accounts.test_access,
  common.test_audit_helpers), the frontend access script and static checks were executed. Before
  deploying: run `python manage.py migrate` and the Django test modules listed in section 7,
  run `npm run build`, then click through each role (super administrator, administrator,
  technician, financial manager, a customised account, a reset account) once.
- On the big device/network pages (device detail, configure, unregistered devices, access
  points, MikroTik) only a "view-only" notice is shown to accounts without the "manage"
  permission; the individual buttons are NOT all hidden. The server refuses any change the
  account may not make, with a clear message, so this is cosmetic - but a tidy-up would gate each
  button with usePermissions().can(...). The device page also still shows its console and
  credentials panels to accounts lacking devices.console / devices.credentials (the server
  refuses them).
- Staff notification "read" state is shared by everyone who can see a notification (one row, one
  flag). One person marking a network notification read marks it read for the other staff who
  can see it. Per-person read state would need a small extra table.
- The audit log grows without limit and has no purge/archive job. Rows are small, but plan for
  retention (e.g. archive rows older than N months) before the table gets large.
- A reset password is "0000" by default. It is protected by the forced change at next sign-in
  (and only works until then), but anyone who learns the convention AND whose account is reset
  and not yet used could sign in as them in that window. Tell the person straight away, or set
  DEFAULT_RESET_PASSWORD to something less guessable.
- A suspended customer cannot change their password (suspension blocks writes), so a reset
  suspended customer is stuck on the change-password page until restored.
- check-access.mjs holds a COPY of the permission catalog; if accounts/access.py changes and the
  copy doesn't, the script can pass while the real rules differ. Update both together.
- No real payment gateway integration. Every payment (customer purchase
  or admin-recorded) is written straight to the database as COMPLETED;
  there is no actual charge against MTN MoMo / Orange Money / a bank
  API anywhere. Online customer purchase currently returns a clear
  "payments unavailable" error until a gateway is wired in
  (payments/services.py - is_gateway_configured / PaymentGatewayNotConfigured).
  Admin-recorded payments and grants work today because they don't go
  through a gateway.
- NOTE: the banner on the admin Payments page ("Coming soon - not yet
  wired in") still lists "automatically reconnecting a customer once a
  payment is confirmed" as not implemented. That is now out of date -
  automatic reconnect-on-payment was implemented and is described in
  section 3.3. Only the payment-gateway line in that banner is still
  accurate. This banner text needs updating in
  frontend/app/pages/admin/payments.vue.
- No self-service password reset ("forgot password") flow exists yet -
  only change-password while already logged in. Customer accounts are
  created by an admin, not self-registered.
- Sign-in has no rate limiting or lockout on the server: repeated wrong passwords are
  not throttled. Recommended next step (DRF scoped throttle on both login endpoints).
- There is still no "forgot password" flow for either kind of account.
- Primary action buttons are still TEAL (--color-secondary), not the brand blue; only
  --color-primary was changed. Changing secondary too would make buttons blue.
- The product images themselves must be placed in frontend/devices/
  (named <icon id>.png, as the catalog JSON references them). Until a
  device's image is there, that device shows the generic icon - the
  feature works without them, just without pictures.
- The catalog is Ubiquiti's. MikroTik routers (and any unlisted model)
  get no stored picture and show the generic router/radio icon. Adding
  aliases for board codes the catalog doesn't list (e.g. bare "P5B") is a
  data task, not a code change.
- Device detail's Network card is display-only: IP/gateway/DNS are what
  the device reports, and editing them there would not change the device.
  Changing a device's network settings is not implemented.
- Node's queue of pending router actions is in memory (a restart loses it). The
  resends in 3.2.2 recover from that, but persisting the queue in Node would
  remove the cause.
- `metered_macs` is parsed but unused; its meaning needs confirming (3.2.2).
- Speed limits cannot be confirmed from the router (no acknowledgement path,
  no queue data in its report). The first real test on hardware should check a
  device's actual speed.
- A changed plan speed is not pushed to customers already on the plan; they
  get it at their next activation, or an admin sets it by hand. A "re-apply to
  everyone on this plan" action was not built.
- Firmware only appears once Node forwards the peers list (3.1.4).
- No automated frontend test suite.
- If you find something else that's missing or broken, add it here
  rather than only mentioning it in chat/Slack, so it doesn't get lost.


## 2026-11 update — staff security and audit UI

### Django admin URL
Application superadmins still carry Django's compatibility flags, but Django admin is not exposed. The backend redirects `/admin/` and nested `/admin/...` URLs to the Nuxt `/staff/login` page. Set `AIRFIBER_FRONTEND_URL` to the production Nuxt origin; otherwise the development default (`http://localhost:3000`) is used.

### Main superadmin
`User.is_main_superadmin` identifies the unique main superadmin. Migration `accounts.0004_main_superadmin` selects the oldest active superadmin from an existing database (oldest overall if none are active); verify the result after deployment. A conditional unique database constraint prevents multiple main accounts. Only the current main account can transfer the designation to another active superadmin, and the transfer requires recipient email, actor password, and acknowledgement. The main account cannot be demoted, deactivated, or deleted until it transfers authority.

### Staff account management
The Staff Accounts page uses a single expandable account row. Its chevron opens details and available actions; opening another account closes the previous one. If a confirmation/edit/reset/transfer workflow is open, the user is asked whether to cancel it before switching. The main superadmin is identified discreetly by a star (not a text label); the Grant main authority action appears in another superadmin's expanded details.

By default, Administrators manage customer accounts but do not see Staff Accounts. A superadministrator may explicitly grant `staff.manage`, which permits managing subordinate technician/finance profiles and resetting their passwords. `staff.delete_subordinates` is a separate permission required for permanent deletion. Staff creation and permission assignment remain superadministrator-only. The backend subordinate-list endpoint explicitly sets `StaffAccountSerializer` to avoid DRF's missing-serializer 500.

Deletion is a permanent staged process: type the target email, then enter the acting user's current password and acknowledge the consequence. Only the main superadmin can delete/deactivate another superadmin. The main account cannot be removed or deactivated until leadership is transferred. Deletion and leadership transfer are audited.

### Staff profile and inactivity timeout
Normal staff profile name, email, and phone are read-only in the UI and profile API. My Account presents the features available to the account without explaining permission administration or showing audit capabilities to non-superadmins. Staff sessions are signed out after 20 minutes without activity in the Nuxt staff layout. The timeout is a frontend control and does not replace JWT expiry, refresh-token revocation, or backend authorization.

### Audit Log
The Audit Log page now uses a responsive filter panel and expandable event cards with distinct field-change and request-context sections. Entries remain read-only, and secrets are not rendered.


### Main-superadmin staff-account boundary (2026-11-07)
Only the main superadministrator can create, edit, deactivate, delete, or reset the password of another staff account. The staff update endpoint includes email and is protected server-side. Individual staff can update their own first/last name and phone via the profile endpoint; their email is read-only there, and they can change their own password using the password-change endpoint. The staff-list avatar shows the main authority marker as a bright SVG star attached to its upper corner.

### Private Django admin route
The built-in Django admin remains redirected from `/admin/` and nested `/admin/...` paths. A configured `DJANGO_ADMIN_PATH` (default `airfiber-maintenance-7x9k2p/`) mounts the Django dashboard at the alternate path. Set a unique value in deployment environment. The URL is only obscurity; continue requiring Django superuser authentication and protect the server.
